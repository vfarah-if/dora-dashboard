# 40. Accept a finding from the clone with a reason, and reopen it when it changes

Date: 2026-10-19

## Status

Accepted

## Context

ADR 0033 lists untriaged findings as a negative, because nothing the dashboard finds in a clone could be set aside. A repository can hold a finding that is true to the reader and false in practice, such as the four Vite mode `.env.*` files that are matched by name only, or a condition that guards a job in a way the reader cannot prove (ADR 0039). Such a finding holds the grade down for as long as it exists, and the only remedy was to change the repository for the sake of the tool. GitHub's own alerts have a remedy already, since they are dismissed on GitHub and the dashboard respects that.

## Decision

A person can accept a finding that the dashboard read from the clone, with a reason and a short note. The accepted finding leaves the grade and the advice, stays visible in an Accepted section with a way to undo it, and reopens by itself when the flagged thing changes. Code scanning, Dependabot and secret scanning alerts cannot be accepted here, and the page says that they are dismissed on GitHub.

- **What can be accepted.** Every supply chain line that the clone produces, whether graded or advice, and the absence of a file or tool such as a dependency review. An acceptance names a check, a path (null only for an absence) and a fingerprint.
- **Fingerprints.** They are worked out at report time in `packages/core/src/securityAcceptance.ts` and are not stored with the facts, so a later change to how one kind is made only needs a new prefix, which reopens every acceptance of that kind instead of matching nothing quietly. A workflow finding uses `w2:` and a hash of the risk, file, line hash, evidence and reach hash, joined with a NUL character so that a bar in one field cannot be read as the end of another. The line hash covers the whole line with its whitespace collapsed, quoted text included, and the reach hash covers every route that reaches the line and every condition it rests on, with no cap (ADR 0039). A changed line, such as a download address inside quotes, a swapped or added caller even past the caps, and an edited or deleted guard therefore reopen it, and an edit above the line does not. An action use uses `a1:` and a hash of `action@ref`. A key file or a Dockerfile uses `b:` and its git blob id. A missing lockfile uses `p1:` and the absence of a file or tool uses `n1:`. `FINGERPRINT_KINDS` holds these kinds and `RETIRED_FINGERPRINT_KINDS` holds `w1`, which hashed only the routes kept for display. A stored row that carries `w1` still loads and reads as reopened while its check finds something in its file, or as gone, a new acceptance takes current kinds only, and a request with a `w1` fingerprint answers 409 `acceptance_finding_changed`.
- **Blob ids without opening the file.** The git adapter runs `git --literal-pathspecs -C <dir> ls-tree -r -z HEAD -- <paths>` in batches of 100 paths, with no token, and keeps regular files only. It reads tree objects and never the file, so a key file is still never opened (ADR 0032). The inspector asks only for key files and Dockerfiles. A failed `git ls-tree` is reported by the adapter as an upstream error with its own message, and the inspector then saves the facts with every blob null and `blobsRead` false and answers `partial`. Code health counts that as an attempt for the head but stores no failure, because the facts are usable, so the page does not show the repository as failed, and the record counts as stale, so the next crawl reads it again even at the same head, until `MAX_INSPECTION_ATTEMPTS`, which is 2, is reached for that head. Only a git failure is handled in this way, and any other error takes code health's unexpected-error path, which saves no facts and records a failed attempt. A key file with a null blob while the lookup was read, such as a listed path that the commit's tree does not hold as a regular file, is not stale. The stored shape check requires the `blob` key on every key file and Dockerfile.
- **Applied in one place.** `supplyChainFound` splits every list into open and accepted findings, so the grade, the advice and the report agree. `remoteActions` still counts every remote use, so the share of unpinned actions keeps its base. A self-hosted finding is split into open and accepted only when the repository is known to be public. With the visibility unknown the check is unmeasured and no acceptance is counted as having applied to it. The grade reads `facts.acceptances`, the what-if used for the path to the next band stays separate, and the report states the band and the supply chain band before acceptance whenever something matched.
- **Four statuses.** An acceptance `applies` when it matches a finding of the latest read. Otherwise it is `unchecked` when the latest read could not check it, which is when there is no supply chain record, when it is for a key file or Dockerfile whose file is still flagged while the blobs were not read or its blob is null, and when it is for `selfHostedPublic` or an accepted absence of a security policy while the repository is not known to be public. It is `gone` when no open finding of that check is left in its file, and `reopened` when something of that check in that file is open again, which is decided for each file.
- **Storage.** The `security_acceptances` table holds the check, the path (an empty string stands for none, because a unique key treats nulls as distinct), the line, the fingerprint, the reason, the note and the time. A key of repository, check, path and fingerprint is unique, and rows go with their repository. The summary's key for acceptances is the count and the highest id among the rows held, so an accept raises it, because `AUTOINCREMENT` never reuses an id, and a removal lowers the count. A row that cannot be read is left out and logged once, so the finding counts again, and the report carries `acceptancesUnreadable`, the count of such rows, which the Accepted section shows as a line when it is above zero, and accepting that finding again replaces the unreadable row with a new one instead of answering that it is a duplicate.
- **No person.** The note, written in the dashboard, is the only free text stored in security data. No login, session value or token is stored or returned, and the service is never handed the session. The rule for the note lives in core's `noteProblem`, which trims it and then requires 1 to 280 code points and no character from U+0000 to U+001F or U+007F, so a line break is refused. The service and the store's read-back use it, the route schema keeps only cheap bounds, and the form blocks Enter and shows a control character as soon as it appears. The line comes from the matched finding and the time from the clock. The note is printed with the page, so its hint tells the writer to include no name and no secret.
- **Routes.** `POST /api/repos/:id/security/acceptances` answers 201 with the acceptance and `DELETE /api/repos/:id/security/acceptances/:acceptanceId` answers 204. Both check the origin and the session. Each allows 30 requests a minute, counted separately, because the installed `@fastify/rate-limit` cannot share one bucket between routes, where the Jira consent routes allow 20 (ADR 0023). An unknown repository or acceptance answers 404. Four conflicts answer 409, checked in this order and carrying the codes `acceptance_no_record` for no record, `acceptance_finding_changed` for a finding that is not in the latest read, `acceptance_limit` for a repository already holding 500 acceptances and `acceptance_duplicate` for a finding already accepted, and the web says each once, in the form while the form stays on the page and in the Accepted section when it leaves.
- **Defaults chosen by the owner of this repository.** An acceptance has no expiry, because reopening on change is enough and the band before acceptance is always shown. Any signed-in session may accept, as it may already change repositories. An accepted absence or missing lockfile stops applying once the file or tool appears.
- **The page.** The Accepted section is always on the page, so a person can see that nothing is accepted as well as what is.

## Consequences

### Positive

- A false positive no longer holds a repository's grade down, and the grade says what acceptance changed, so a reader of the list can tell High from High after accepting a finding that was Low.
- An acceptance reopens when the line, the action reference, the key file or the callers change, so it cannot outlive the thing that was judged.
- Reading blob ids from the tree costs one command for each 100 paths and keeps the rule that a key file is never opened.

### Negative

- Who accepted a finding cannot be shown, because no person is stored. That keeps ADR 0008 and ADR 0031 intact, and it leaves a team to record the decision elsewhere if it needs an author.
- A team can raise its own band by accepting findings. The band before acceptance is shown on the grade, the list and the printed page to offset that, but it relies on the reader looking.
- Identical lines with the same reach in one file share a fingerprint, so one acceptance covers all of them, and a new copy of an accepted line is accepted without anyone seeing it. The Accepted section says how many places an acceptance covers.
- A changed condition, or a change among the routes past the display caps, reopens an acceptance, and so does a route going away, because the reach is part of the fingerprint. That is accepted, since the person judged the finding as it was reached.
- Any signed-in session may accept, so a person with no standing on a repository can accept its findings. The check for push access was left out and can be added later without changing the stored data.
- Every acceptance stored with `w1` reopens once, and the person has to accept the finding again under `w2`.
- A key file whose blob could not be read shows its acceptance as unchecked, and the finding counts until the next good read, because it cannot be accepted or matched without its blob. A failed lookup is read again at the next crawl, and a persistent failure stops after two attempts for one head.
- The line hash covers quoted text, so a short secret written in a quoted string on a flagged line could in principle be guessed from the hash by someone who can read the stored facts. The line is already readable in the repository itself, and the hash is never the text (ADR 0039).
- The note is free text that is printed, so nothing stops a person from typing a name or a secret into it other than the hint beside the field.
