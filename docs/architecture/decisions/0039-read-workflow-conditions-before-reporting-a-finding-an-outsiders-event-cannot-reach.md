# 39. Read workflow conditions before reporting a finding an outsider's event cannot reach

Date: 2026-10-19

## Status

Accepted

## Context

One repository's security grade was Low because of a single false positive. A reusable workflow checked out `github.event.workflow_run.head_sha`, and the analyser reported it because the file inherits `workflow_run` from the workflow that calls it. The analyser never read an `if:` condition, so it could not see that the calling job ran only for runs that a push had started, which no outsider can cause. A finding also said nothing about why it was reported, so a person could not tell a proven risk from a limit of the reader.

## Decision

The workflow analyser in `packages/core` reads `if:` conditions and reports a step only when some event an outsider can cause is not provably kept from it. Anything the reader cannot prove counts as a finding, so a guard can remove a finding only by having been proved.

- `workflowExpressions.ts` holds a tokeniser, a precedence parser and an evaluator that answers true, false or unknown. It follows GitHub's documented rules for coercion, case-insensitive strings, `&&` and `||` returning their operands, the status functions and the implicit `success() &&`. A string that is not a JSON number but looks numeric, such as `0x10`, `+1`, `1.` or `Infinity`, is unknown when it is compared with a number, because the runner reads more forms than JSON does and a comparison taken as false could hide a finding. Text over 2,000 characters, 500 tokens or 32 levels, and anything it cannot parse, is unreadable.
- `workflowReach.ts` models each trigger as attack worlds. There are two `workflow_run` worlds, one for an upstream run headed by a fork and one for an upstream run headed by the base repository, one world each for `pull_request_target`, `pull_request`, `pull_request_review` and `pull_request_review_comment`, and one for each comment or issue event. The review triggers start fork worlds that belong to the pull request set and are never privileged, because GitHub gives a fork's run of them no secrets. Only the event name, the repository identity and the head repository's fork status are known, so a branch filter, a label gate or a test of the repository's name against a literal, such as `github.repository == 'acme/widgets'`, is never a guard, since the fork guard compares two names by identity.
- In the fork-headed world `github.event.workflow_run.event` is one of `pull_request`, `pull_request_review` and `pull_request_review_comment`, and in the base-headed world it is any event other than those three and `push`, `schedule`, `workflow_dispatch`, `repository_dispatch` and `merge_group`. Compared with a literal it is false for a name it cannot be, true only for a set of one name, and unknown otherwise, and it is unknown inside any function and against anything that is not a string. A `!=` against each of the three pull request names in turn therefore stays unknown, and so does a comparison of the event with a number or a `contains` call on it, although GitHub would give false.
- A condition is read only when its text is an expression and nothing else. `${{ }}` is unwrapped only when the untrimmed text starts with `${{` and ends with `}}`, and any other text holding `${{` is unreadable, because GitHub then builds a `format()` string that is always true. A block scalar keeps its final line break unless its indicator holds `-`, so a wrapped `|`, `>` or `|+` block is unreadable. A wrapper around one string literal, such as `${{ '' }}`, is unreadable, because GitHub reads that string as the condition. A value that runs past 200 rows is unreadable, and a dotted string index such as `github['event.workflow_run.event']` is unknown. A local `uses:` path is normalised for `.`, `..` and repeated slashes, and a path that climbs above the root matches nothing.
- The two `workflow_run` worlds differ as GitHub documents. A `pull_request_target` workflow "runs in the context of the default branch of the base repository", so in the base-headed world, which holds the run that follows one, `github.event.workflow_run.head_repository.*` is the base repository (the base's own value, with `fork` false), and `head_branch`, `head_sha` and `head_commit.*` are the base's own and not the outsider's. Only `display_title` and `pull_requests` still come from the outsider. In the fork-headed world all of them do. Which worlds a finding needs therefore depends on the reference it matched. For `prHeadCheckout`, a `workflow_run.head_sha` or `head_branch` reference counts in every head world except the base-headed one, while `workflow_run.pull_requests`, a `head_repository` reference and every other head reference count in all of them. For `scriptInjection`, `workflow_run.head_branch` and `head_commit.*` leave that world out in the same way, and `display_title` and every other untrusted reference count in all privileged worlds.
- Jobs are visited in `needs` order, and a job whose direct need is known not to run gets a false implicit `success()` and does not run either, following the documented chain rule. Each need's own result already counts that need's own needs, so a job that runs because its condition says `always()` hands its dependants a running need, and they are reported again. `needs.<id>.result` reads `skipped` only for a need that is known not to run.
- `reachOf` replaces the joined caller triggers with routes, each holding the worlds that the calling jobs' conditions leave open. A file holds at most 20 routes and a chain at most 10 calls, and past those limits one stand-in route per trigger treats the callers as unguarded.
- `prHeadCheckout` reads the head worlds, `scriptInjection` and `persistCredentials` the privileged worlds, and the `onPullRequest` flag of `selfHosted` the pull request worlds. Every other risk is unchanged.
- A finding records `routes` and `conditions`, at most three of each, with counts of the rest, and carries a required `lineHash` and a required `reachHash`. Both are computed with FNV-1a over 64 bits without `BigInt` or `node:crypto`, because the web app imports core. The line hash covers the whole line with its whitespace collapsed, quoted text included, so changing a literal such as the address of a download changes it and reopens an acceptance (ADR 0040). The reach hash covers every route that reaches the line and every condition it rests on, with no cap, which means every condition of the calling jobs along each route and every condition of the line's own step, its job and the jobs that job needs. Each condition counts by its file, a hash of its text as written with whitespace collapsed, and its truth in each world, with no line numbers. The conditions kept for display, at most 20 of the line's own and six on each route, count again with the verdict they are shown with, a route past the three shown still counts although its conditions are not listed, and the stand-in route for routes past the limits covers the conditions of every caller's call. A finding with no reach has the constant hash of the empty text. Neither hash is ever the text.
- Text that is stored, which is a condition shown beside a finding and the evidence of a script injection, passes through one tokenising blank. A quoted string becomes `''`. A quote that is never closed, a double-quoted string holding a backslash and a backslash directly before a quote of either kind cannot be told from a literal that runs on, so the rest of the text is replaced by `''` and a marker. Anything from a `#` outside a string is cut. A literal, which may be a hardcoded token, is therefore never stored. The result is a branded type, so storing text that was not blanked does not compile.
- `SUPPLY_CHAIN_VERSION` is raised from 3 to 5, so stored facts are read again on each repository's next crawl.

## Consequences

### Positive

- The common guards stop false findings, and the reported case is cleared without any change to the repository's workflows.
- Each finding says which trigger and which calls reach it and which conditions did not stop it, so a person can see whether to add a guard or to accept the finding.
- Anything the reader cannot prove is unknown and kept, so a missing proof never hides a finding.

### Negative

- The reader imitates GitHub's semantics, and a mistake in that imitation, such as a wrong coercion, could hide a real finding, because a known answer that is wrong removes a finding that an unknown answer would have kept. For that reason each rule that answers true or false is pinned by a hand-stated test, and breaking the needs rule, the identity rule or the Kleene rule was shown to fail them.
- Guards it cannot prove stay flagged, such as the outputs of a job that runs, inputs, variables, labels and a test of the head branch, so some false positives remain and need accepting by a person.
- The base-headed world rests on GitHub's documentation that a `pull_request_target` workflow runs in the default branch's context. If GitHub's behaviour differed, a `head_sha` or `head_branch` checkout behind a fork guard would be hidden although an outsider reached it. A reference to `display_title` or `pull_requests` counts in that world as well, because an outsider writes both.
- A reference to `workflow_run.head_sha` or `head_branch` in a file that GitHub starts for another event, such as a comment, is still reported, because the reader does not model that the value is empty there.
- GitHub documents no operator precedence, so the reader follows the runner's order, which matters for no guard form in use.
- A fork guard on a self-hosted job removes the graded `selfHostedPublic` finding, although the job is still listed.
- Facts are read again after the version bump, and until a repository's next crawl its supply chain part is unmeasured, so its grade can read higher in that window.
- The hash of a line is not a secret. It covers the whole line, quoted text included, so a short secret written in a quoted string could in principle be guessed from the hash by someone who can already read the stored facts. The line is already readable in the repository itself, and the stored text and evidence are blanked, so the hash adds a way to check a guess and no new way to read the line.
