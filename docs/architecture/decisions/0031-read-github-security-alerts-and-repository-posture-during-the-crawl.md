# 31. Read GitHub security alerts and repository posture during the crawl

Date: 2026-10-11

## Status

Accepted

## Context

The dashboard shows delivery flow, DORA, code health and issues, but says nothing about security, although GitHub already holds Dependabot, code scanning and secret scanning alerts, and the rules that protect the deploy branch. The crawl holds a token (ADR 0004) and has already shown that a further GitHub read can be added behind its own port without a new credential (ADR 0028, ADR 0030). Reading the alerts during the crawl, and storing them, gives trends, time to fix and a comparison across repositories that a live read would not. The shapes are in `packages/core/src/securityTypes.ts`.

## Decision

**A port of its own.** `SecurityAlertSource` has one adapter for GitHub, wired only in `main.ts` and `cli.ts` (ADR 0003). It returns alerts in core's shape, so no service sees a GitHub field name, and a second code host would be a second adapter. The port also gives the page where features are switched on (`settingsUrl`), so no service names a host, and the report's settings link is empty when no adapter is wired.

**What is read.** The three alert endpoints (`dependabot/alerts`, `code-scanning/alerts` and `secret-scanning/alerts`) and, for the deploy branch only, branch protection, the rules that rulesets apply to the branch, the repository's security settings (security updates, push protection, validity checks and private vulnerability reporting) and its own security advisories, counted by state. Rules and advisories are read 100 to a page, for at most 5 pages.

**Credentials.** The existing `repo` scope suffices, because `X-Accepted-OAuth-Scopes` lists `repo` for all three alert endpoints, which was checked against a live repository. A fine-grained token needs read permission for each of Dependabot alerts, code scanning alerts, secret scanning alerts and repository security advisories. Dependabot and code scanning alerts also need the person behind the token to have at least the Write role. Secret scanning alerts need a repository or organisation administrator, as do classic protection detail and the `security_and_analysis` settings, which an organisation owner or a security manager can see as well, and automated security fixes need administrator read access. Ruleset rules, the branch's protected flag and private vulnerability reporting need only Metadata, which every fine-grained token has.

**Each source on its own.** Every source is read independently and stored with a status of `ok`, `off`, `no_access`, `not_used` (OSV only, ADR 0034), `error` or `not_read`, each with the reasons that belong to it. Only a 401 fails the crawl, as in ADR 0028. Any other failure, including one from the store, is recorded against the stage that raised it and the later stages still run. The stored message for a refusal is "GitHub answered 502", with GitHub's own JSON `message` added only when it is one of a known set of phrases (rate limit, resource not accessible, must have admin rights, SAML enforcement, bad credentials, requires authentication or not found), because any other text from GitHub is free text from upstream (rule 9). A transport failure gives "GitHub could not be reached", a rate limit with the time it lifts, or a neutral message when the failure was unexpected. No stored message carries the token, and any query string in an address is removed. An `error` state keeps the last good read only when the state before it was `ok` or an `error` that had one, so one bad read hides nothing that is still true, and a failure after `no_access`, `off` or `not_used` cannot bring back alerts that were not in use. A rate limit is recognised before a 403 is taken to mean that a feature is switched off, and a 403 or 429 whose message says rate limit counts as one even without GitHub's headers. Only exact messages mean off: a 403 saying Dependabot alerts are disabled, a 403 saying Advanced Security must be enabled or that code scanning is not enabled, and a code scanning 404 saying "no analysis found", because that 404 is otherwise sent to a token that cannot see the list. Any other 403, such as a single sign-on block, is an error. A source that is `off` has its stored alerts cleared, whereas `no_access` keeps what a more privileged token stored and records only the state, so a less privileged crawl wipes nothing. The kept alerts are not counted while the source says `no_access`.

**Paging and transport.** The adapter asks for 100 alerts a page, follows the `Link` header only to an https address on the API's own origin, and reads at most 10 pages per source. A source that holds more is marked truncated, and so is one whose next link was refused (another origin, http, an address that cannot be read or a header over 4,096 characters), because the list went on. Stored alerts are pruned only after a complete read, which is one that was not truncated and left out no alert that could not even be numbered. An alert that has a number but could not be mapped counts as present, so its stored copy stays and does not block the pruning of the rest. The count of alerts that could not be mapped is kept on the source. Redirects are followed by hand, at most three and only to https on the origin of the request, so the token cannot leave GitHub's API host. A reply is read to a cap of 16 MiB and a body that is not JSON is an upstream error. A failure to reach GitHub, such as a name lookup, a TLS error or a reset connection, is an upstream error that says so and carries no address. A deploy branch name with a `.` or `..` segment is refused before any request.

**Privacy.** Secret scanning is always requested with `hide_secret=true`, and the secret value is never mapped, stored or returned, and no stored field is called `secret`. People fields (who dismissed, resolved or bypassed, and assignees) and free text (comments, rule help, advisory descriptions and instance messages) are never mapped either, in keeping with ADR 0008. An alert's title is the advisory summary or the rule description, which is published text and not a person's. No login appears in any security response.

**Posture failures.** A failed posture read is stored beside the earlier posture, which is kept, with its message and time, and the report carries both as `postureFailure` so the page can say that the branch facts are from an earlier read. A read fails, and saves no posture of unknowns, on a rate limit, on a 403 that is not a permission refusal and on a 404 for the repository or the deploy branch. Only a 403 saying the resource is not accessible or that admin rights are needed, or a 404 from an endpoint that only an administrator or a plan with the feature can read, leaves that one part unknown.

**Storage.** Alerts, source states and the repository posture go in new SQLite tables (ADR 0005) that cascade when a repository is removed. A stored alert, source state, supply chain record, posture or Scorecard result that cannot be read back is left out or treated as not held, and logged, so one damaged row never fails the report of another repository. Dependabot and OSV alerts store the severity mapped when they were read. Code scanning and secret scanning severities are worked out at report time from the raw facts, as ADR 0028 does for issue kinds, so changing those rules needs no crawl.

## Consequences

### Positive

- Trends, time to fix and cross-repository comparison need no live calls, and the page loads from stored data.
- A repository without a paid GitHub product, or a token with fewer rights, still gets a report for the sources that could be read, with the reason for each gap stated.
- No new credential, consent step or external system is needed.

### Negative

- Each crawl makes more GitHub calls, up to ten pages for each of three alert sources plus the posture reads, which counts against the rate limit on large estates.
- GitHub gives no reopen history, so an alert reopened after a fix reads as open from its creation, and a read stopped at ten pages shows only the most recently updated alerts.
- Alerts are as fresh as the last crawl, so a new alert or a fix does not show until the next one.
- Settings and classic protection detail that need an administrator show as not visible for most tokens, which is not the same as switched off, and the page has to say so.
- Alerts are read with the token of whoever crawled and are then shown to everyone signed in to the dashboard, although GitHub limits secret scanning alerts to administrators. An operator who crawls with an administrator's token shares what that token can see.

## Revision History

- 2026-10-12: Recorded the permissions in full, the failure messages and their scrubbing, that `no_access` keeps stored alerts and only `off` clears them, the stricter reading of code scanning's 404, the manual redirect rule, the reply cap, stored posture failures and the shared token as a negative consequence.
- 2026-10-12: An unprotected branch is now fully known. When the branch read says `protected: false`, or classic protection answers 404 "Branch not protected", the classic part is reported as read and `detail` is `full` when rulesets were also read; other 404 and 403 answers still mean not visible. Private vulnerability reporting and repository security advisories are requested only when the visibility is `public`, because GitHub answers 404 for a private repository even to an administrator. Weakness ids are normalised to `CWE-<number>`.
- 2026-10-12: Statuses became a union with each reason tied to its status, `not_used` was added for OSV, and an error keeps its last good read only from `ok` or an earlier error. Rate limits without headers, exact switched-off messages, refused next links as truncation, paged rulesets and advisories, GitHub's own error texts, posture failure classification (`postureFailure`) and the adapter's settings URL are recorded. Severity is stored for Dependabot and OSV alerts and worked out at report time for the other two, and a damaged stored row costs only its own repository.
- 2026-10-12: GitHub's own text is kept in a stored message only when it is a known phrase, and otherwise the message says only the status (rule 9). A ruleset list cut at the page cap or a refused next link gives `detail` `none` when nothing seen is enforced and `rulesets_only` when something is, so `full` means the rulesets were read in full. A one-time migration clears the read time of `error` source rows written by the earlier build, which therefore have no last good read, and a posture table without its attempt time is rebuilt.
